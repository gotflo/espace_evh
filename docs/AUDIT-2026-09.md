# Audit de la plateforme EVH — septembre 2026

Audit réalisé avant toute modification : lecture du code, mesures locales, tests automatisés, vérification de la
production (en lecture seule : codes HTTP, en-têtes, temps de réponse ; aucun contenu sensible consulté) et analyse
des captures hPanel fournies (ressources, PHP, cron, test de vitesse).

---

## 1. Architecture actuelle

```
Navigateur (PWA React)
   │  HTTPS — CDN Hostinger (hcdn, Brotli, HTTP/3)
   ▼
Apache + PHP-FPM 8.3 (LiteSpeed/CloudLinux, 1 cœur, 2 Go, 40 workers PHP)
   │  public/.htaccess → index.php (Laravel)
   ▼
Laravel 13 ── /api/* (Sanctum, permissions, périmètres) ── MySQL
   │         └─ /{page} → renvoie index.html (application React)
   ├─ Services (Notifier, FissService, ReportService, CalendarService…)
   ├─ Automatismes : cron « schedule:run » chaque minute → app:tick (idempotent)
   └─ Push : Web Push VAPID, envoyé après la réponse HTTP (defer), en parallèle
```

| Élément | Constat |
|---------|---------|
| Backend | Laravel 13.17, PHP 8.3, Sanctum 4, 37 contrôleurs, 30 modèles, 12 services, 16 classes utilitaires, 130 routes API |
| Frontend | React 19, TypeScript, Vite, React Router 7, 25 pages, 38 composants, PWA (service worker) |
| Base | 43 tables, 49 migrations toutes réversibles |
| **Triggers SQL** | **Aucun.** Toute la logique métier est dans les services PHP (testable, versionnée). À conserver ainsi. |
| **Jobs / files d'attente** | **Aucun worker** (`QUEUE_CONNECTION=sync`), ce qui est cohérent avec l'hébergement mutualisé : les traitements différés passent par `defer()` (après la réponse) et par le cron idempotent `app:tick`. |
| Événements / listeners | Aucun : les effets de bord sont appelés explicitement par les services (lisible, pas de logique cachée). |
| PDF | Générés **dans le navigateur** (pdfmake chargé à la demande) : aucune charge serveur, aucun fichier stocké. |
| Tests | 88 tests (permissions, AP multi-tribus, FISS, familles, rapports, charge, injections, concurrence, vidéos, cultes). |

## 2. Cartographie fonctionnelle

- **Utilisateur** (téléphone) → 1 **profil** → **une seule tribu** (`profiles.tribe_id`), un GEM, plusieurs départements.
- **Rôles** attribués avec une portée (`role_user.scope_kind/scope_id`) : un **AP** peut recevoir plusieurs tribus ;
  un membre n'a qu'une tribu. Rôle « Responsable » supprimé (→ responsables de département). « GAD » → **Garde**.
- **FISS** mensuelle (unique par membre et par mois), verrouillée, modifiable sur demande validée (2 max, verrou).
- **Vertumètre** = moyenne des notes (/20) données par les responsables *(à remplacer par un questionnaire rempli
  par le membre : en attente des questionnaires)*.
- **Assiduité** = présences aux cultes et répétitions.
- **Famille** : conjoint (lien confirmé des deux côtés) ou nom seul, enfants, date de mariage.
- **Publications** (annonces, événements, exercices) : portée multiple (église, tribus, GEM, départements).
- **Notifications** : centre in-app + push, priorité, lien, anti-doublon (`notification_dispatches`).
- **Rapports** : église / mes tribus / une tribu, 3-6-12 mois, PDF ; **Journal d'audit** en lecture seule.

## 6. Limites de ce qui peut être mesuré

- **Charge simultanée réelle** : un vrai test à 500 utilisateurs simultanés doit viser un serveur équivalent à la
  production. Le lancer sur le site en ligne gênerait les membres : non effectué sans votre accord. Un script k6 est
  fourni (`scripts/load/k6-scenario.js`) pour une fenêtre calme ou un sous-domaine de test.
- **Volumes** (500 → 5 000 membres) : mesurés localement, sur SQLite, dans le processus (voir le rapport final).
  Les chiffres absolus diffèrent de MySQL/Hostinger ; ce qui compte est l'évolution avec le volume.
- **Concurrence stricte** (deux processus au même instant) : les verrous `lockForUpdate` et contraintes d'unicité
  sont vérifiés par les tests ; SQLite sérialise les écritures, MySQL applique les verrous de ligne.

## 7. Plan d'action

1. **Hébergement et performance** : drapeaux chargés à la demande, polices servies par le site, page HTML servie
   directement par Apache avec cache long des fichiers versionnés, en-tête PHP retiré, vrais 404 pour les fichiers
   manquants, recommandations PHP, rotation des journaux.
2. **Observabilité** : `/api/health` (base, cache, cron, disque) et trace de chaque passage des automatismes.
3. **Passage à l'échelle** : liste des membres paginée (recherche serveur) et sélecteur de fidèle par recherche.
4. **Contenu** : versets du tableau de bord administrables par PR et PA (brouillon, programmation, rotation, aperçu).
5. **Automatisation** : rapport mensuel envoyé aux responsables ; accueil « Content de vous revoir ».
6. **Notifications** : préférences par catégorie (push), sans jamais masquer l'essentiel.
7. **Réseau mobile** : bandeau hors ligne, brouillons conservés (FISS, réponses, messages).
8. **Accessibilité** : focus clavier visible partout, zones tactiles.
9. **Mesures de volume** 500 / 1 000 / 2 000 / 5 000 membres, script de charge, documentation, commit.

## 9. Deuxième passe : MySQL, charge simultanée, concurrence réelle, pannes, parcours

Tout ce qui suit a été **mesuré**, sur un poste Windows (16 cœurs logiques), en reproduisant le forfait :
serveur web limité à **1 cœur** et **40 processus PHP**, PHP 8.3 avec OPcache, **MySQL 8.4**, caches Laravel
de production, base de **5 500 membres** (12 mois de FISS, présences, 100 000 notifications). Limites de
l'exercice : PHP sous Windows est nettement plus lent que sous Linux (démarrage de Laravel 8 à 27 ms selon le
montage, contre quelques ms attendues chez Hostinger) et le cache est en base au lieu de fichiers (voir 9.3) :
**les chiffres sont pessimistes** et ne remplacent pas le test sur l'hébergement réel (marche à suivre :
[`A-FAIRE-DE-VOTRE-COTE.md`](A-FAIRE-DE-VOTRE-COTE.md), étape 6).

### 9.1 Volume sur MySQL (2 → 5 000 membres)

`DB_CONNECTION=mysql BENCH_SIZES=2,50,100,250,500,1000,2000,5000 php artisan test --group=benchmark`.
Médiane de 10 appels (ms) ; le nombre de requêtes SQL de chaque écran reste **identique** à toutes les tailles.

| Écran | 2 | 50 | 100 | 250 | 500 | 1 000 | 2 000 | 5 000 |
|---|---|---|---|---|---|---|---|---|
| Membre · pouls (calcul commun, sans cache) | 5 | 6 | 6 | 8 | 10 | 13 | 21 | 43 |
| Membre · profil `/me` | 7 | 8 | 7 | 8 | 13 | 8 | 7 | 8 |
| Membre · calendrier du mois | 28 | 33 | 31 | 30 | 31 | 36 | 45 | 64 |
| Pasteur · membres (page 1) | 9 | 24 | 27 | 29 | 48 | 36 | 44 | 67 |
| Pasteur · rapport église 12 mois (sans cache) | 22 | 41 | 64 | 134 | 233 | 467 | 953 | 2 396 |
| Pasteur · suivi d'un exercice pour toute l'église | 7 | 15 | 22 | 48 | 87 | 171 | 405 | 964 |
| AP 3 tribus · rapport 6 mois (sans cache) | 16 | 27 | 30 | 46 | 65 | 114 | 242 | 526 |

Le « pouls » à 43 ms est le calcul **commun** (mis en cache 10 s pour tout le monde) ; la part propre à chaque
appareil est une seule requête indexée.

**Problème trouvé et corrigé** — sur MySQL, chaque écriture est validée séparément sur le disque. Le premier
passage des automatismes à 5 500 membres prenait **3 min 40 s** (dont 191 s pour les rappels de profil). Les
écritures sont maintenant groupées par lots de 200 dans une transaction : **11 s** au total, rappels de profil
**8 s**. Anti-doublon inchangé ; les notifications push partent après la validation du lot.

| | Avant | Après |

les mesures ci-dessus utilisent donc le cache en base (plus coûteux : estimation prudente).

### 9.4 Concurrence réelle (requêtes réellement simultanées, MySQL)

| Cas critique | Avant | Après |
|---|---|---|

| FISS : 10 demandes de modification | 1 demande | 1 demande (verrou déjà en place) |
| Tribu : 10 demandes de changement | 1 demande | 1 demande (verrou déjà en place) |

### 9.5 Pannes volontaires (tests `RecoveryTest`)

- **Base injoignable** : réponse 503 claire (« Le service est momentanément indisponible… », `Retry-After`),
  aucun détail technique ; `/api/health` passe à `down` ; tout refonctionne dès le retour de la base.
- **Service de notifications push en panne** (erreur 503 ou délai) : la notification dans l'application est
  enregistrée quand même, l'appareil n'est pas désinscrit.
- **Envoi automatique qui échoue en cours de route** : la clé anti-doublon est libérée, le message part au
  passage suivant du cron, une seule fois.
- **Étape des automatismes en panne** : les suivantes tournent quand même ; `/api/health` signale l'étape en échec.

### 9.7 Accessibilité

81 champs de formulaire n'avaient pas de nom lisible par un lecteur d'écran (étiquette visible mais non reliée) :
tous nommés, plus 12 champs traités à la main (recherches, notes FISS « Méditation (sur 20) »…). Textes
uniformisés au vouvoiement (accueil, message d'anniversaire).

- **Contraste** (calculé, norme WCAG AA = 4,5:1) : texte principal 16,5:1, secondaire 5,9:1, liens 7,5:1,
  messages d'erreur / succès / information 5,1 à 6,6:1. Le texte « discret » (dates, aides) n'avait que 3,0:1
  (2,8:1 sur le fond de page) : assombri à 5,3:1 (4,7:1 sur les champs).
- **Grandes tailles de texte** : police à 150 % sur un écran de 360 px, aucun débordement horizontal (accueil,
  fiche, calendrier, notifications, contact, profil, vie spirituelle).
- Les informations ne reposent jamais sur la couleur seule : statuts écrits (« Actif », « Inactif », « À démarrer »…).

### 9.8 Présentation plus sobre

Environ 150 emojis servaient d'icônes ou de décoration dans les textes, les états vides et les titres de
notifications (🎉, 👋, 📢, 🙌…). Ils sont remplacés par des icônes au trait monochromes (les mêmes que le menu,
`utils/icons.ts`) ou simplement retirés. Conservés à la demande : les visages de « Ma vie spirituelle » et
l'icône du rappel de fiche du mois. Restent aussi les signes typographiques sobres (✓, flèches, ↻ pour
« récurrent », étoiles de note) et les drapeaux du choix du pays.

|---|---|
| Centralisées, historisées, lu / non lu, priorité | `Notifier::send` → table `user_notifications` (type, priorité, lien), cloche et page Notifications |
| Dédupliquées, idempotentes | clé unique par envoi automatique (`notification_dispatches`), libérée si l'envoi échoue (nouvel essai au passage suivant) |
| Contextualisées, liées à une action | titres précis (« Votre fiche de septembre… », « Anniversaire aujourd'hui : … ») et lien direct vers l'écran concerné |
| Adaptées au rôle | destinataires calculés par périmètre (`Recipients` : responsables de la tribu, du GEM, du département) |
| Regroupement | récapitulatifs : anniversaires du jour par responsable, programme des cultes la veille, nouveaux inactifs le lundi, rapport mensuel |
| Préférences | chaque membre coupe le push par catégorie ; tout reste dans la cloche |
| **Limitation** (nouveau) | au-delà de 6 notifications dans l'heure pour une personne, plus de push sauf urgence (tout reste dans la cloche) |
| **Nouvelle tentative** (nouveau) | push en échec passager (délai, 429, 5xx) renvoyé une fois ; refus définitifs non renvoyés ; appareil désinscrit seulement s'il n'existe plus (404/410) |
| Une panne ne fait pas tomber l'application | envoi push isolé (après la réponse, ou après la transaction en tâche planifiée), erreurs journalisées ; testé (`RecoveryTest`) |
